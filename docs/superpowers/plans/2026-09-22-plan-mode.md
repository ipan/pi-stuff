# Pi Plan Mode Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a session-scoped Pi extension mode that safely prevents workspace mutation while producing plans that may be explicitly exported as Markdown.

**Architecture:** A `extensions/plan-mode` extension owns mode state, its active-tool snapshot, and safe plan export helpers. Entering plan mode narrows active tools; event gates block LLM tool calls and user shell commands as a defense in depth. A slash command, shortcut, and CLI flag control the persisted session state, while `/save-plan` is the only extension-owned filesystem mutation and requires confirmation.

**Tech Stack:** TypeScript, Node.js `node:test`/`node:assert`, Pi Extension API, Node `fs/promises` and `path`.

**Spec:** `docs/superpowers/specs/2026-09-22-plan-mode-design.md`

## Global Constraints

- Do not change Pi core.
- Do not automatically implement a saved plan or save a plan at turn completion.
- Do not classify arbitrary shell commands as read-only; block both LLM `bash`/`powershell` and user `!`/`!!` shell commands in plan mode.
- Enforce plan mode through active-tool restriction and execution gates; system-prompt instructions are supplemental only.
- In plan mode retain only `read`, `grep`, `find`, and `ls`; leave unknown/custom tools inactive.
- Restore the exact pre-plan active-tool set on exit, intersected with tools currently available.
- Persist mode transitions as custom session entries, without absolute paths or secrets.
- `/save-plan` must require explicit confirmation, resolve paths inside the workspace, and obtain all filesystem mutation through extension-owned code.
- Noninteractive modes must not silently write a plan.

## Review Focus

- A later extension or a stale provider tool declaration can expose `write`, `edit`, `bash`, `powershell`, or an unknown custom tool; it must still be blocked by the plan-mode `tool_call` gate. **Task 2** pins this.
- A user can bypass the LLM tool interface using `!` or `!!`; both forms must return a non-executing result in plan mode. **Task 2** pins this.
- Entering plan mode after a customized tool loadout must restore precisely that loadout rather than enable tools that were previously absent. **Task 1** pins this.
- A resume/fork/reload may restore a persisted plan state when some formerly active tools no longer exist; exit must restore only current known tools. **Task 1** pins this.
- A supplied export path can escape through `..`, point at an existing file, or be used in print/JSON mode; the extension must reject it or require confirmation before any write. **Task 3** pins this.

Create `extensions/plan-mode/state.ts`. Implement the functions from the interface with these rules:

```ts
export function activePlanTools(allToolNames: readonly string[]): string[] {
  return allToolNames.filter((name) => PLAN_SAFE_TOOLS.has(name));
}

export function restoreActiveTools(restoreTools: readonly string[], allToolNames: readonly string[]): string[] {
  const available = new Set(allToolNames);
  return [...new Set(restoreTools)].filter((name) => available.has(name));
}
```

- [ ] **Step 3: Implement the plan-mode extension and safety gates**

Create `extensions/plan-mode/index.ts` with a default `function (pi: ExtensionAPI): void`.

Register `pi.registerFlag("plan", { description: "Start in read-only plan mode", type: "boolean", default: false })`, the `/plan` command, a temporary `/save-plan` command that only notifies `Plan export is not available until plan saving is enabled.`, and `ctrl+shift+p` shortcut. The command/shortcut must call a shared `setPlanMode(enabled, ctx)` function that:

1. Calls `await ctx.waitForIdle()` before changing policy.
2. On entry, snapshots `pi.getActiveTools()`, invokes `pi.setActiveTools(activePlanTools(pi.getAllTools().map((tool) => tool.name)))`, and appends `pi.appendEntry(PLAN_MODE_STATE_TYPE, createPlanModeState(true, snapshot))`.
3. On exit, invokes `pi.setActiveTools(restoreActiveTools(state.restoreTools, pi.getAllTools().map((tool) => tool.name)))` and appends the disabled state.
4. Updates `ctx.ui.setStatus("plan-mode", "PLAN")` when enabled and clears that status when disabled. Notify `Plan mode enabled: workspace mutation is blocked.` or `Plan mode disabled: previous tools restored.` when `ctx.hasUI`.

On `session_start`, restore the last valid state from `ctx.sessionManager.getBranch()`. If the CLI flag is true on startup, enable it; otherwise activate safe tools if restored state is enabled. Do not append another state entry during restoration. Apply/clear the status.

Register `before_agent_start`: when enabled, return `{ systemPrompt: planModeSystemPrompt(event.systemPrompt) }`, where the appended instruction says exactly that the agent is in plan mode, may investigate using read-only tools, must prepare a proposal, and must not modify the workspace or ask to bypass controls.

Make `shouldBlockPlanTool` return `false` only for the four names in `PLAN_SAFE_TOOLS`. In `tool_call`, if mode is enabled and the tool is blocked, return `{ block: true, reason: PLAN_MODE_BLOCK_REASON }`. In `user_bash`, if enabled, return `{ result: { output: PLAN_MODE_BLOCK_REASON, exitCode: 126, cancelled: false, truncated: false } }` so neither `!` nor `!!` reaches the local shell backend.

- [ ] **Step 4: Replace the temporary `/save-plan` response with the confirmed export flow**

In `index.ts`, import the plan helpers. `/save-plan [path]` must:

1. Reject when `ctx.hasUI` is false with `Plan export requires an interactive confirmation.`; do not read/edit/write a file.
2. Resolve the requested/default path; notify the validation error and stop on rejection.
3. Get `latestAssistantText(ctx.sessionManager.getBranch())`; if absent notify `No assistant proposal is available to save.` and stop.
4. Open `await ctx.ui.editor("Save plan", proposal)`; stop when it returns `undefined`.
5. Render the edited content; notify and stop if empty.
6. Ask `await ctx.ui.confirm("Save plan?", \\`Write ${relative(ctx.cwd, target)}?\\`)`; stop unless true.
7. Call `writePlanFile`, then notify `Plan saved to <relative path>.`; notify the caught error without throwing.

The command must be available in normal and plan modes, but its only mutation is this confirmation-gated export.
